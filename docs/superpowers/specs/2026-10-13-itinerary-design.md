# 行程规划设计

用户已确认上一轮提出的下一阶段：需求收集、知识与天气驱动的规划、多轮修改。本阶段沿用该范围，不包含前端、地图路线或交易执行。

采用独立结构化后端工作流，而不是纯文本攻略或新增多 Agent 系统。纯文本难以验证预算和资料来源；多 Agent 会增加调用成本和调试复杂度。现有 DeepSeek 负责提取需求及选择候选景点，Java 负责检索、MCP 调用、校验、费用计算及保存。

接口 POST /api/itineraries/plan 接收 conversationId、message；GET /api/itineraries/{conversationId} 读取最新状态。与聊天使用同样的会话标识，但结构化行程状态单独存储，避免随最近20条聊天历史被裁剪。

需求字段：城市、出发日期、天数（1—7）、单人预算、偏好、希望全部安排室内活动的天序号。缺少城市、日期、天数、预算时返回追问；后续消息仅更新明确提供的字段。预算仅核验单人已知门票费用，明确交通、餐饮、住宿未计，不声称满足完整出游总预算。

景点来自 category=itinerary-attraction 的知识文档，其 content 是短 JSON，包含 name、city、indoor、ticketPrice、visitHours、source、demo、closedWeekdays。模型只返回候选文档编号，不能填写新景点或票价。Java 检查日期、日程数量、重复景点、室内要求、每日至多3处、游览时长至多6小时、闭馆日与门票预算；不生成精确交通耗时。每日至少一处；资料不足或不符合需求时返回调整提示，不编造填满。

最多查询前4个可预报日期，每请求最多4次天气工具调用，超过预报范围、服务不可用或未启用agent时标记未获取。模型基于天气选择室内安排；输出保留按天的天气与来源。雨天备选使用同一天可用的室内候选资料，并标注仅为候选、未计入费用。

DeepSeek 输出 JSON，经字段类型校验后使用；纯文本偏好数组可规范成字符串，其余无效类型拒绝。无deepseek模式返回明确未启用提示。模型错误、校验不通过不覆盖旧行程。Redis启用时以24小时TTL保存，使用版本号原子比较更新；默认内存实现相同的版本语义。同会话并发修改冲突返回409，避免覆盖新结果。

局部室内修改以新旧限制的差异确定受影响日期。未修改日期的完整编号清单在模型调用前作为固定日程提供，调用后由Java恢复并统一校验，防止模型把保留景点重复放入新日程。资料检索先按行程类别过滤，再限制候选数量。

测试：缺字段追问、合并修改、隔离会话、无知识、虚构景点拒绝、闭馆／室内／时长校验、超预算、天气失败与调用上限、失败保留原状态、并发版本冲突、模型兼容HTTP格式、接口校验、真实Redis保存及TTL。最终以真实DeepSeek、本地向量、MCP完成两日行程与修改演示。
